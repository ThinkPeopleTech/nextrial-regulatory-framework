# Regulatory Validation Framework for AI in Clinical Trials

**An open standard for how AI systems in clinical trials get verified.**

---

> *The model proposes; the proof disposes.*

---

## What This Is

Clinical trial AI is being deployed faster than the regulatory guidance governing it. The result is inconsistent, undocumented, and often unauditable practice — varying by sponsor, CRO, site, and jurisdiction.

This repository publishes a formal specification for how AI outputs in clinical trial activation and execution should be verified. It defines the architecture, the proof artifact, the human oversight mechanisms, and the regulatory mappings for four major jurisdictions.

The framework is built on one foundational principle:

**A regulated clinical decision must be reconstructible — source data, decision logic, and rule application — at the moment an inspector asks for it.**

Confidence scores cannot do this. Proof certificates can.

The canonical source of truth is the framework paper, **[Toward a Regulatory Validation Framework for AI-Assisted Clinical Trial Activation](papers/regulatory-validation-framework-v3.md)** (v3.0, June 2026), the companion to NexTrial.ai's public comment on FDA Docket No. FDA-2026-N-4390. Every specification, schema, and reference artifact in this repository derives from it.

## The Framework at a Glance

### The Verification Pipeline: an RBQM Pre-Gate and Three Uncorrelated Gates

```
┌──────────────────────────────────────────────────────┐
│  RBQM PRE-GATE: Risk Before Verification             │
│  Assigns and freezes the risk class                  │
│  Model influence × Decision consequence              │
└──────────────────────────┬───────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────┐
│  GATE 1: Deterministic Compliance Verification       │
│  "Is this output compliant?"                         │
│  Rule-type-agnostic · Deterministic · Pass/Fail      │
└──────────────────────────┬───────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────┐
│  GATE 2: Structural Proof (Lean4)                    │
│  "Can we prove structural correctness?"              │
│  Machine-checkable · Reproducible · Concentrates     │
│  the encoding-fidelity risk into one inspectable place│
└──────────────────────────┬───────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────┐
│  GATE 3: Human Oversight and Attestation             │
│  "Does the responsible human accept, reject, or ask?"│
│  Two attestation levels · Override + escalation record│
└──────────────────────────────────────────────────────┘
```

The three gates are **uncorrelated by design**: a deterministic rule check, a formal structural proof, and a human attestation are three substrates whose errors are unlikely to share a common cause. A confidence score is the opposite — it is generated by the same model whose output it scores, so it inherits that output's blind spots.

### The Proof Certificate: Eight Properties

Every AI-assisted decision subject to this framework produces a **proof certificate** — a machine-readable, signed, versioned artifact, produced at the moment the decision is made, that serializes eight properties. The first four define what was checked and what was reserved for the human; the second four make the artifact defensible under inspection, accountability, and continuous learning.

1. **Rule invoked** — the specific rule by source, citation, and version (regulation, protocol criterion, SOP step, or jurisdictional requirement), with snapshot version and effective date.
2. **Values verified** — the exact values checked, listed not summarized, each attributable to source per ALCOA+.
3. **Verification operation** — the deterministic procedure that returned pass/fail, expressible as a formal predicate, with bit-exact reproducibility as the standard.
4. **Boundary statement** — what was *not* checked, in four parts: verified scope, reserved scope, reviewer obligations, escalation criteria.
5. **Risk classification** — the class the RBQM pre-gate assigned and froze at decision time, with a named, versioned taxonomy, indexing gate rigor and re-verification cadence.
6. **Human reviewer identity** — the identity and role of the human who attested, bound to the attestation.
7. **Override and escalation record** — whether the human chose **ACCEPT**, **REJECT**, or **ASK**, with any challenge and its resolution (including mitigate-and-rerun), any override rationale, and any escalation destination.
8. **Evidence, not substitution** — an explicit declaration that the operation is evidence presented to the reviewer, not a substitution for the reviewer's judgment (default; substitution is prohibited by construction for CRITICAL and HIGH decisions).

Full specification: **[specs/proof-certificate-spec-v3.md](specs/proof-certificate-spec-v3.md)**. Normative schema: **[reference/proof-certificate.schema.json](reference/proof-certificate.schema.json)**.

### Provably Right, Not Probably Right

Hand the proof certificate to an inspector. Ask: *"Can you reconstruct this decision from this artifact alone?"* If yes — it satisfies the framework. If no — it is not a compliance artifact. It is a metric.

## What Is Open

Everything in this repository is open: the architecture specification, the proof certificate schema, the regulatory mapping tables, the attestation protocol, the adapter interface contract, the Lean4 type definitions, the reference implementation and conformance harness, and the co-development record.

The standard belongs to the industry.

## What Is Protected

The production implementations that satisfy this standard — the functional regulatory compliance adapters, the predictive eligibility layer, the lineage-memory subsystem, internal protocol-structuring representations, the deployment infrastructure, and proprietary model artifacts (trained weights, adapters, and fine-tuning data) — remain proprietary to NexTrial.

The boundary is explicit. See [BOUNDARY.md](BOUNDARY.md) for the complete delineation.

## Open Questions

The framework states honestly what it has not closed (paper §9). The questions are led by the one the framework most wants help with:

1. **Who certifies the encoding** — when a regulation is encoded into a computable check, who certifies that the encoding is faithful, and who is accountable when the check is structurally perfect and semantically wrong. This is the framework's principal unsolved problem.
2. **Cross-agency proof-certificate standardization** — the minimum property set regulators would agree to accept.
3. **Risk-taxonomy harmonization** — a shared taxonomy across the FDA, the EU, ANVISA, and the CDSCO.
4. **Patient equity at the architectural layer** — handling demographic-accuracy disparities for predictive eligibility.
5. **Cross-jurisdictional mutual recognition** — moving reliance from plausible-in-principle to operational-in-practice.
6. **Escalation enforcement and arbitration**, and **mapping to the Predetermined Change Control Plan**.

Details and current positions: [/co-development/open-questions.md](co-development/open-questions.md)
